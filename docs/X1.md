# Experimental xTool X1 / JS001

This fork adds **discovery-only basic monitoring**, not full X1 support. The
X1 is registered as `JS001_V2`; it is not an alias of the M2 (`JS002`).
Upstream attribution and the MIT license are preserved.

## What is implemented and evidenced

The reviewed X1 answers encrypted V2 unicast `deviceFind` discovery. The profile
uses that existing discovery wire format and requires the exact device code
`JS001`, platform `2.0`, a nonempty serial, name and firmware, and a unique reply
for the configured address. It binds subsequent refreshes to the saved serial.
It creates only:

- Advertised name, firmware, model code and platform diagnostic sensors.
- **Discovery reachable**, meaning a valid response was received at the last
  poll. It does not mean authorized, operational, idle, or safe to run.

The minimum refresh interval is 60 seconds. Missing, ambiguous, changed-device,
wrong-model and malformed replies fail closed; identity sensors become
unavailable rather than publishing invented defaults. UDP discovery is not
cryptographic device authentication: its shared encryption keys are already
part of the upstream implementation. Do not expose this protocol to the internet.

## Cameras and attached Bluetooth accessories: blocked, not supported yet

The signed xTool Studio Desktop 1.10.15 application explicitly identifies
`X1` / `JS001` as a V2/platform-2.0 device. Its X1 extension and shared worker
provide useful **source evidence**:

- Machine identity: `GET /v1/platform/device/machine-info`.
- State snapshot: `POST /v1/platform/device/state/sync`.
- Camera enumeration: `GET /v1/platform/camera/list`.
- X1 image capture: `POST /v1/platform/camera/snap`, with a camera name.
- Attached accessory enumeration: `GET /v1/platform/accessories/list`.

These routes are not hardware-success claims. The live test opened the device
TLS WebSocket but its unmodified upstream guest parity request returned
**406: connection identifier or version mismatch**. Studio's current
`ParityService.handleParityResponse` treats 406 as requiring the user's device
button authorization and stops when interactive pairing is disallowed. The
experiment stopped there: no auth-status polling, new pairing, token extraction,
protected status/capability/accessory request, image capture, movement or setting
change was performed. No live camera or attached-accessory response shape was
obtained. The discovery-only profile therefore has **no camera, accessory,
operational-status, laser-head or safety-state entities**. It does not call the
protected API or substitute discovery for its authorization.

Adding cameras/accessories requires a separately authorized normal device
connection, reviewed credential persistence/session-token handling, and actual
read-only responses. Do not borrow an app token, suppress parity errors, send
unreviewed M-codes, scan/pair Bluetooth devices, or guess response shapes.

## Safety and trust boundaries

The X1 protocol deliberately has no WebSocket/instruction/control transport,
request passthrough, job services, writable entities or firmware updater. Its
coordinator inherits the empty base factories, not the M2/F-family factories.
Firmware updates stay disabled even if inherited options request them. Existing
models and upstream authentication/TLS behavior are otherwise unchanged.

The original WS-V2 transport accepts self-signed certificates. Studio 1.10.15's
signed application also installs a permissive certificate callback. Neither is
manufacturer-CA identity verification. The test inspected the device-supplied
xTool Trust Root chain but did **not** install it as a trust anchor; the one
private handshake probe was constrained to the exact leaf previously observed
at the independently correlated owner endpoint. This is not a public CA trust
claim. No certificate/private endpoint identifier is included here. Any future
X1 protected-API implementation must review device trust without lowering
upstream protections or treating a peer-supplied root as independently trusted.

## Installation and verification status

Use the native Home Assistant Marketplace custom-repository flow with this
fork, and select the model labelled **xTool X1 (experimental discovery only)**.
Do not install it alongside another `xtool` component. Accept Marketplace's
custom-code warning yourself in Home Assistant if you choose to proceed; this
experiment did not accept it or copy files around that gate. Activation may
require a separate owner-approved **Core-only** restart after a configuration
check. No host/Supervisor/unrelated restart is required by this change.

The profile and entity factories are tested against Home Assistant 2026.11.1
using a sanitized real discovery response and error/identity-change regressions:

```sh
python -m unittest discover -s tests
```

Source tests, direct device reads, installed files, loaded HA integration, and
HA entities are separate gates. The original experiment was **not installed or
activated in Home Assistant** because its Marketplace warning was unaccepted.
Camera and Bluetooth support remains incomplete regardless of discovery tests.
No real frames, tokens, serials, MAC addresses, private addresses or vendor
application bundles belong in this repository or diagnostic logs.
