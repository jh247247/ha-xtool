# Experimental xTool X1 / JS001

This fork adds X1 read-only status, on-demand camera snapshots and connected-only
Bluetooth inventory. `JS001_V2` is an independent X1 profile, not an M2 alias.
Legacy models keep their existing transports and behavior.

## Supported observations

With an imported owner-issued grant, the integration reads:

- Protected machine identity, checked against the bound serial and `JS001` code.
- Raw REPORT fields `mode`, `moveState` and `gohomeState`. The observed values
  were `Idle`, `idle` and `finish`. These are not safety or readiness assertions.
  An absent field is unknown; a failed refresh makes entities unavailable.
- Onboard accessory slot connectivity, reported status and application firmware.
  Slot 71 is the dongle. Its presence does not prove a purifier or fan exists.
  Empty `common_status` stays unknown, not idle or successful telemetry.
- Connected-only Bluetooth inventory using the signed-source `M9098` query.
  The actual response was `M9098 none`: zero connected peripherals. A missing or
  offline dongle gives unknown inventory, not a successful empty query. Nonempty
  rows require an explicit status and validated fields; only diagnostic type
  prefixes and a connected count are exposed. Their telemetry is unverified.
- Far, near and side JPEG snapshots, requested on demand. All three were verified
  by the controller. Camera-list `nv12` describes streams, not snapshot format.
  No LDM image entity, ranging, exposure, lighting, movement or live video is used.

`POST /v1/platform/device/state/sync` returns `{}`, not a state snapshot. It
requests REPORT messages. The integration never interprets it as idle or reads
M2 `curMode`. Empty capabilities do not establish any capability.

The minimum polling interval is 60 seconds. No arbitrary request service,
writable entity, job operation, firmware operation, Bluetooth scan, pairing or
per-accessory telemetry command is provided. X1 also ignores inherited power
switch and firmware-update options.

## Private grant import

Installation and activation remain owner actions. Use the native Home Assistant
Marketplace custom-repository flow and the **xTool X1 (experimental read-only)**
model. Do not install beside another `xtool` component. Accept the custom-code
warning yourself if proceeding. Any needed Core-only restart is a separate
approval; this work does not accept the warning or restart Home Assistant.

After creating the discovery entry, open its options and choose **Grant**. Paste
the controller's integration-owned JSON grant into the masked field. The exact
fields are `host`, `serial`, `client_id`, `consumer`, `leaf_sha256`, `user_id`,
`timezone` and `token`. Do not use Studio account data, copied Studio credentials,
a cloud token or fresh pairing. No live grant belongs in this repository.

The grant must preserve the existing host, serial, canonical client UUID and
original leaf SHA-256 pin. Its consumer is exactly
`jh247247/ha-xtool:X1:camera-accessory-investigation`, and its normal parity user
is `mk-guest`. This user name does not authorize a tokenless guest fallback.
The controller can combine its independently validated binding and permanent
credential in memory without changing any bound value.

Import is bounded to 16 KiB. Fields are bounded individually, including an
8192-character token limit. No identifier is normalized. Home Assistant stores
the grant using private, atomic storage under `.storage/xtool.x1_grant.<entry_id>`
and reads back the exact grant before reporting success. Options contain only
the configured flag and polling interval, never the grant or session token.
Protect Home Assistant storage and backups as credentials.

When no grant has intentionally been configured, discovery-only identity and
reachability remain available. Once configured, a missing, invalid or refused
grant fails closed. It never falls back to discovery, tokenless parity, a new
UUID, cloud credentials, button polling or refreshed certificate trust. Reimport
an owner-reviewed grant to replace it; failed authorization does not clear it.

## Transport and snapshot checks

X1 does not inherit the legacy WS control transport or its permissive TLS rules.
Every socket uses the same bound client UUID and exact certificate fingerprint,
refuses redirects, and has bounded connection and operation timeouts. Normal
parity sends the existing permanent token; subsequent envelopes use the
memory-only session token. A returned changed permanent token is refused.
Trust is the exact previously established leaf pin, not manufacturer-CA
authentication. The integration never automatically refreshes that pin.

Snapshots use only direct `POST /v1/platform/camera/snap` for an enumerated,
admitted camera. Only its just-issued filename can enter the private download
path. The pinned `file_stream` socket opens before the download handshake and
stays open through successful finish. Transfer checks include the size bound,
CRC framing, channel, contiguous offsets, packet limits, exact size, MD5 and JPEG
format/dimensions/decoding. Failed finish is a failure, without retries or cached
image success. Images are not persisted by this integration.

## Verification and remaining gates

Run the offline suite with Home Assistant 2026.11.1 and its camera dependencies:

```sh
python -m unittest discover -s tests -v
```

The suite uses a local synthetic TLS peer, sanitized observed shapes, generated
JPEGs, real HA coordinators/entities and private storage. It checks refused
authorization, binding/pin/redirect failures, unknown and unavailable states,
empty versus offline Bluetooth inventory, corrupt transfers and failed finish.
Cold HA imports and the supported grant options flow are exercised separately.

Source verification, controller direct-device evidence, installed files, loaded
HA integration and actual HA entities are distinct claims. The controller
directly exercised the exact accepted production transport: authenticated
`poll_readonly()` and far, near and side snapshots all succeeded, including JPEG
verification and transfer finish. The connected Bluetooth query reported zero
peripherals. This revision has **not been installed or loaded in the owner's
Home Assistant**. Per-accessory telemetry remains unverified because no
physically connected peripheral was available. Live video remains unverified;
opening a passive media channel without receiving frames is not video proof.
